# Workflows

A workflow is a saved, versioned plan whose stages pass evidence and receipts to each other. It fits multi-stage build, review and fix work or a longer unattended task. Check workflows_catalog for current availability, premades, bindings and limits before proposing work. Copy a premade to make an editable definition; a run keeps its frozen version.

Plan, build, review and fix plans the task, builds it, reviews the result and makes bounded fixes before the owner's final gate. Council then build gathers separate supplied-evidence views, synthesizes a plan and builds with review and fixes. Sprint divides a task into dependent units and works through their build, review and fix stages before the owner's gate and report. Actual models and review independence come from the coverage card, not these names. In a started stage with read access, the Reviewer can list, read and search the run's workspace files using the same scope and read limits as the Builder. The Reviewer cannot change files or run commands or tests. It must identify any difference between the current workspace and the frozen review evidence. Ordinary Reviewer chat still reviews supplied evidence.

Assistant discusses ideas until the user asks for a plan or work; Planner prepares plans directly. Plan with the user first. Explain what will be done, the call and time budget, and what will remain unverified. Proposing freezes the definition, inputs, workspace, models, skills, checks and budget into a coverage card. It appears in the owner's Needs you with who proposed it. Proposing grants no authority and starts nothing. Only the owner's Start click runs it. Start, Resume and owner gates are not model tools. Saving a definition is separate from starting it.

The card offers “Work without asking in this workspace” or “Ask before each change.” The first follows Builder Auto within the run's workspace and definition's upper bounds. Anything Auto would still ask about keeps asking. The second asks before each change. Neither changes the global mode or grants unrestricted execution. Questions, approvals and owner gates appear under Needs you. Steering messages queue at safe boundaries; they cannot answer owner gates, replace pinned acceptance or widen the grant. Same-model review requires an explicit owner choice and is recorded as a downgrade.

Follow the run in its originating Assistant or Planner conversation or Runs. Open stage conversations to inspect work, read budget and check receipts, answer Needs you items and read the final report. A run from an Assistant or Planner conversation stores its deterministic report first, then uses one budgeted summary call by that originating agent when budget remains. Check the report for any skipped summary and for omitted evidence. No deterministic checks means no claim that checks passed. Review by a model is not independent filesystem or test verification. Publication requires its own receipt.

Accepted and queued mean admitted or waiting, not completed work. Running means work is in progress. Needs you waits for a question, approval or gate. Pausing and stopping may still be cleaning up. Paused work needs the owner's Resume click. Recovery after interruption needs an owner decision and does not certify the interrupted stage. Completed, stopped, expired, failed, blocked and unknown are different end states: completed reports the recorded work; stopped records a requested stop; expired records a spent time or grant limit; failed records a known failure; blocked records unresolved work; unknown leaves an uncertain outcome. Read reasons, checks, cleanup and caveats before claiming success.

Outside agents use the scoped MCP tools workflows_catalog, workflows_list, workflows_get and workflows_propose, then workflow_run_status, workflow_run_events and workflow_run_report. Use workflow_run_message for scoped steering and workflow_run_stop to request a stop. Keep returned IDs and reuse the exact request key and arguments after a lost acknowledgement. MCP cannot start or resume a run, answer a gate, save or delete definitions, or choose an Assistant or Planner origin. The gateway enforces the token's owner and scope; hidden resources look like not found. Event observation supports a wait of up to 25 seconds; respect a rate-limit retry delay. Closing observation never cancels execution.
