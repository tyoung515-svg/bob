# Live limits and stopping
Values below are read from the same face/configuration/policy sources the runtime uses. A face override takes precedence over the configured tool-loop limit. At that limit an interactive chat turn with a bound question channel asks the owner whether to Keep going or Stop here. Only a committed answer to this platform question grants another block of the same size. At most three extensions are allowed, so the Assistant starts with 50 rounds and can reach 200 total; Builder starts with 100 and can reach 400. Other agents keep their own block sizes and can reach four times that limit. After the three extensions, Stop here, a question timeout or cancellation, the runtime stops without an extra model call, keeps visible progress and says it has not finished. Reply "continue" to carry on in a new reply. Workflow stage turns, outside-agent MCP calls and turns without a bound question writer keep their existing stop. Budget and rate limits still apply. The completion frame and final stored message metadata record step_extensions (0 through 3); platform step questions carry origin: step_limit in their frame and stored question/answer metadata. The turn is marked stopped_reason: tool_round_limit; raw tool results are not included in the stop notice. Backend context enforcement may trim context before transport.
The portal also has an active-work stream cap, separate from model/tool rounds. Human-question and Builder approval waits pause that work clock but have their own bounds. stream_deadline is a stopped turn, not proof of a broken runtime. Broker defaults below are shipped source defaults; the core cannot observe a particular client broker CLI override.
On a desktop lane, the backend's fanout width of 20 caps workers per wave in the older graph dispatch path; ordinary desktop chat and workflow stages do not use that path, so it gives the desktop owner no usable concurrency allowance. The workflow catalog's effective_worker_slots of 1 describes the installed worker capacity for workspace jobs, not all model calls. Its workflow_parallelism of 2 limits concurrent items in a workflow's foreach stage; two model turns can overlap while workspace jobs still share one worker slot. The separate run_controller_limit of 2 bounds active workflow controllers in the lane.
An expired never-approved PC request means nothing ran; check Needs you before retrying. pc_turn_window_ended means the authenticated PC turn window ended; a new user message can continue work. Neither is proof a runtime is stuck; Windows Repair is for an app-reported stuck runtime. Approval expiry ends the turn cleanly. Unknown outcomes require reconciliation, never a fresh mutation replay.
Builder commands are bounded and output may truncate; report exits, timeouts, denial and cleanup failures. Text/team/job limits depend on the specific saved run and admission receipts. Discover budgets/blocked seats in work_catalog or external list_agent_services rather than inferring them from an old team name. Paused, failed, cancelled and unknown states are not success. Read the current run's budget and wall deadline.
